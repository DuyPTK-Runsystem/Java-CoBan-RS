- Assigned role `STUDENT` to the newly created account.
- Added explicit `username` and `password` request fields.
- Added default username generation: normalized full name plus the final seven StudentCode digits.
- Added initials fallback for long names, for example `Phạm Trần Khánh Duy` -> `ptkd1234567`.
- Added default password `12345678`, stored only through `PasswordEncoder`.
- Response exposes safe account data only: user id, username and role; no password/hash.
- Preserved the existing v1 Student create flow.

## 4. Implementation decisions

- Account creation is isolated in `StudentAccountService` so the existing `StudentService` does not exceed the project's PMD coupling/method thresholds.
- The v3 endpoint is restricted to `ADMIN` and `ACADEMIC_OFFICE`.
- Explicit usernames are validated by the request DTO; duplicate usernames and student codes return `409 Conflict`.
- Generated usernames respect the existing 20-character `app_user.user_name` column. Full normalized names fall back to initials before the final length limit is applied.
- Missing seeded role `STUDENT` returns a typed `500` error before user persistence.
- No database migration was needed because the existing `student.user_id`, `app_user`, `role` and `user_role` structures are reused.

- The account orchestration was placed in a new `StudentAccountService` rather than increasing the existing `StudentService` coupling. API behavior is unchanged from the approved plan.
- No Postman collection update was made because the task only required backend implementation and the existing collection does not yet define this v3 account-creation flow.
- Username collisions remain a conflict rather than an automatic suffix/retry, preserving deterministic account naming.
