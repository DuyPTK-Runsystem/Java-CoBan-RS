## Implemented scope

- Added `/api/v4/timetable-agent` proposal, approval, execution, action receipt, and idempotency-key lookup endpoints. The controller requires ADMIN or ACADEMIC_OFFICE; proposal/action retrieval is actor-scoped.
- Added provider-neutral Spring AI 2.0.1 chat integration using native structured output and gated native tool calling. The gateway resolver rejects multiple ChatModels or gateway adapters, and lazily builds the generic Spring AI adapter only when exactly one ChatModel is present. No provider/model starter or default provider was selected because the user confirmed none is installed. `app.ai.timetable.enabled` defaults to `false`.
- Added bounded proposal generation and repair calls, schema validation, safe provider-usage aggregation, and sanitized HTTP failures. Spring AI framework retries are configured to one attempt; provider SDK retry behavior remains provider-specific and unverified.
- Added immutable proposal payload/hash/expiry, explicit human approval binding, one-tool allowlist and argument equality checks, action PENDING/FAILED/SAVED_DRAFT state, actor/key request-hash binding, lease reclaim, and saved-receipt replay before model access.
- Proposal validation is read-only. The final save transaction uses SERIALIZABLE isolation, locks semester head before target revision, refreshes and fingerprints its source snapshot, revalidates the approved payload, preserves unchanged and locked row identities, applies scoped changes while retaining out-of-range portions, forces the revision version with `PESSIMISTIC_FORCE_INCREMENT` before building the receipt, audits, and returns a server-generated receipt.
- Model input contains aggregate weekly teacher-load targets. Eligibility/homeroom/rule/computed inputs used for invalidation are included only in the server-side fingerprint source, not the model snapshot; evidence references and free-text reasons are excluded.
- Current effective published revision entries are captured as external conflict context. Weekly demand is checked against actual recurring weekdays and closed dates. These behaviors share existing timetable validation/evaluator logic.
- Proposal, snapshot, validation, action-state, model-call, revalidation, and draft-mutation logic is separated into focused helpers. The proposal identity/payload fields are grouped into embeddables while retaining their database column names; the actor-scoped lookup uses an explicit JPQL path through the embedded identity.
- The existing timetable detail capability is now computed from draft status, ADMIN/ACADEMIC_OFFICE authorization, the feature flag, positive configured application bounds, and exactly one gateway with both native capabilities. With no provider or unset bounds, the flag remains false and the existing manual workflow stays available.
- Application bounds have no production numeric defaults: class count, request characters, preference characters, snapshot characters, and proposal entry count default to zero/unconfigured. Enabling the feature requires positive values; request/context sizes are checked before provider calls, and returned entry count is checked before proposal persistence. Provider-specific token limits/retry behavior remain unverified until a concrete adapter is selected.

Do not enable or promote save/pilot until application bounds are explicitly set, MySQL concurrency/phantom behavior is proven against a dedicated disposable schema, and a selected provider passes live native-capability, token, timeout, and retry checks.
