## Actual change

- `FE/src/services/notificationApi.ts`: refresh through the existing callback on **every successful SSE connection**, including the first connection. Previously only reconnects synchronized; a publish between the initial REST snapshot and server subscription could leave the badge stale indefinitely.
- `FE/src/services/notificationApi.spec.ts`: initial synchronization, split LF/CRLF event frames, reconnect, retry cleanup, 401/403 and abort assertions; updated the event test for connection plus event callbacks.
- `FE/src/views/shell/AuthenticatedV2ShellView.spec.ts`: actual stream client with a deferred connection, real navigation layout and controlled unread API snapshots. Assert badge `2` → `3` without any event replay or navigation.
- Developer Plan, this note and FE/global Dev Note summaries.
- No backend source, shell production source, dependency, schema, endpoint or visual changes in this task. Existing uncommitted SSE implementation and the shell's direct badge-refresh callback were preserved.

## Live test data and limitations

- Created local targeted IN_APP test notifications IDs 12–15, without email or broad audience delivery. All four test receipts were marked read; browser unread badge returned to `1`. Existing notifications were untouched. Test notifications remain as read inbox history.
- Steady-state delivery also worked before this connection fix. The deterministic startup gap is fixed, but the user's original intermittent failure was not directly reproduced in the running local browser.
- Runtime logs contained an async security error for a completed/disconnected response; it was not established as the cause of badge failure and no authentication policy was changed.
- One additional REST synchronization on initial connection is intentional; existing latest-request protection in the shell prevents stale overlapping responses from winning.
- One production correction after the expected red regression run. No validation rule suppressions, deployment or commit.
