# Plan 076.3 BE — Notification v3 UX Audience Lookup

## 1. Trạng thái, mục tiêu và approval boundary

- Application-document version: **v3**.
- Liên quan: [Plan 076 BE](076-targeted-notification-2026-09-15.md), [Module 03](../../../application-doc/v3/modules/03-NotificationAndAudience.md), [CR-V3-001](../../../application-doc/v3/change-request/CR-V3-001-academic-operations-and-targeted-communication.md), [FE API boundary](../../../application-doc/v3/frontend-api/README.md).
- Trạng thái: **APPROVED — implementation BE đã được user phê duyệt trong agent message ngày 2026-09-17; validation tách riêng**.

Mục tiêu là bổ sung contract backend cho UX chọn audience `CLASS` và `INDIVIDUAL`: lookup có search/pagination, chỉ trả candidate trong role/school scope hợp lệ, và tạo notification theo biểu diễn canonical để backend vẫn là nguồn quyết định cuối cùng cho existence, eligibility, snapshot và idempotency.

User đã chốt áp dụng các candidate decisions A01–A06 trong agent message ngày 2026-09-17. Plan này ủy quyền triển khai BE trong đúng scope bên dưới; không chạy test/validation trong implementation agent và không đổi FE.

Implementation checkpoint:

- A01: `app_user` hiện không có status; mọi user hiện hữu được xem là active. User linked với student chỉ eligible khi `StudentStatus.ACTIVE`; user không linked được phép chọn theo candidate.
- A02: chỉ `SchoolClassStatus.ACTIVE` thuộc `AcademicYearStatus.ACTIVE`, roster `EnrollmentStatus.ACTIVE`, student active và có user tồn tại.
- A03: search case-insensitive theo `studentCode`, `studentName`, `username`; response tối thiểu theo contract.
- A04: cho phép staff user không linked student vì không có user-status/role policy riêng trong code hiện hữu; role chỉ bảo vệ endpoint manager.
- A05: lớp rỗng/inactive/out-of-year trả `422` ở guard; class ID không tồn tại vẫn giữ `404` tại resolver cũ để tương thích error semantics hiện hữu.
- A06: request mới của `INDIVIDUAL` chỉ dùng `recipientUserIds`; target reference legacy vẫn được đọc khi publish stored data.

## 2. Baseline đã kiểm chứng

- Notification v3 hiện có `POST /api/v3/notifications`, inbox/manage/detail/publish/cancel/read. `ADMIN` và `ACADEMIC_OFFICE` tạo/manage; mọi user đã xác thực chỉ đọc inbox/detail trong access scope.
- `INDIVIDUAL` hiện bắt buộc `recipientUserIds`; `NotificationDraftService` sắp/ghép các ID thành `Notification.targetReference` để snapshot payload. `CLASS` bắt buộc `targetReference` là class ID dương; `SCHOOL` không nhận cả hai field.
- Khi publish, `NotificationAudienceService` kiểm tra user tồn tại cho `INDIVIDUAL`; `CLASS` kiểm tra lớp tồn tại rồi lấy `StudentYearEnrollment` có `ACTIVE` và map `Student.userId`; `SCHOOL` hiện lấy mọi `app_user`. Receipt unique theo notification/recipient bảo vệ duplicate.
- Existing lookup model chưa có endpoint audience UX. `SchoolClass` có `academicYearId`, `classCode`, `className`, status `PLANNED|ACTIVE|CLOSED`; `Student` có `studentCode`, `studentName`, `userId`, status; user chỉ có `username`/roles. Do đó không được để FE tự suy luận eligible recipient từ các list v2.
- Plan 076 là `IMPLEMENTED SLICE — validation incomplete`, không phải điểm xuất phát để thay đổi notification email v2 hoặc tuyên bố mọi gate backend đã PASS.

## 3. Requirement và ranh giới

### In-scope sau approval

- Lookup backend riêng cho audience `CLASS` và `INDIVIDUAL`, search ở backend và `ResultPaginationDTO` zero-based.
- Role guard, single-school `DEFAULT_SCHOOL` validation, existence/eligibility guard lúc create/publish và canonical audience mapping.
- Deduplicate `recipientUserIds`, snapshot recipient lúc publish, fingerprint idempotency và receipt uniqueness theo invariant Plan 076.
- DTO/service/repository read-only tối thiểu trong `notification/**`; chỉ thêm query read-model vào `academic`, `student`, `user` hoặc `enrollment` khi bảng scope file bên dưới nêu rõ.
- Contract tests và regression tests thuộc notification sau khi implementation được phê duyệt.

### Out-of-scope

- FE, route/navigation, fixture/Storybook, notification v2/email/SMTP, role/lifecycle khác Plan 076.
- Thay đổi `SCHOOL` policy, scheduling, retention, content/HTML policy, account provisioning, enrollment/class lifecycle.
- Tự động tạo tài khoản cho student không có `userId`, backfill receipt, bulk resend, migration dữ liệu cũ.
- Migration schema mặc định: lookup/read-model chỉ dùng dữ liệu hiện hữu. Migration chỉ được thêm qua contract checkpoint/amendment nếu evidence cho thấy thiếu constraint/index cần thiết; không tự tạo migration chỉ vì endpoint mới.

## 4. Contract delta đề xuất (chờ chốt)

Các endpoint dưới đây là candidate. Chúng không thay đổi API cũ và chỉ trở thành public contract khi được approval.

| Endpoint | Quyền | Query | Response/result | Mục đích |
|---|---|---|---|---|
| `GET /api/v3/notifications/audiences/classes` | `ADMIN`, `ACADEMIC_OFFICE` | `q`, `page=0`, `size=20` | `ResultPaginationDTO<ResNotificationClassAudienceDTO>` | Chọn lớp eligible cho `CLASS`. |
| `GET /api/v3/notifications/audiences/individuals` | `ADMIN`, `ACADEMIC_OFFICE` | `q`, `page=0`, `size=20` | `ResultPaginationDTO<ResNotificationIndividualAudienceDTO>` | Chọn recipient eligible cho `INDIVIDUAL`. |

`q` là optional, trim trước query, có giới hạn length (đề xuất 100), không là filter giả ở FE. `page` zero-based; request dùng `size`, response dùng `meta.page/pageSize/totalPages/totalItems` theo `ResultPaginationDTO`. Không trả password, role set đầy đủ, enrollment history, internal audit hoặc dữ liệu liên lạc không cần cho selector.

### Candidate response tối thiểu

```text
ResNotificationClassAudienceDTO
  classId, classCode, className, academicYearId, eligibleRecipientCount

ResNotificationIndividualAudienceDTO
  userId, displayName, studentCode? , username?
```

`classId` được FE gửi lại duy nhất qua `targetReference = String.valueOf(classId)` khi create `CLASS`; `recipientUserIds` phải rỗng/null. Với `INDIVIDUAL`, FE gửi duy nhất mảng `recipientUserIds` đã chọn; `targetReference` phải rỗng/null. Backend sort/deduplicate positive IDs trước persistence/fingerprint để cùng tập recipient theo thứ tự khác nhau không tạo resource khác khi dùng cùng idempotency key.

Không đưa `eligibleRecipientCount` vào idempotency fingerprint. Không cho client gửi `displayName`, enrollment, `classCode`, hoặc snapshot recipient; backend resolve và snapshot tại publish.

## 5. Quy tắc xử lý sau thay đổi

```text
Manager -> lookup q/page/size -> backend role + DEFAULT_SCHOOL guard
        -> only eligible candidates -> FE selects canonical IDs
        -> create validates shape + existence/eligibility -> canonical fingerprint
        -> publish rechecks current eligibility -> resolve/snapshot -> unique receipts
```

1. Lookup chỉ là hỗ trợ UX, không cấp quyền: create/publish phải re-check theo cùng policy để chống stale selection, forged ID và race với enrollment/account change.
2. `INDIVIDUAL`: reject ID null/<=0, deduplicate, reject user không tồn tại hoặc không eligible; không fallback parse comma-separated `targetReference` từ request mới. Stored legacy snapshot vẫn phải đọc/publish tương thích theo Plan 076.
3. `CLASS`: reject class không tồn tại hoặc không eligible; resolve roster ở publish từ enrollment hợp lệ và chỉ lấy student có `userId` eligible. Nếu roster sau filter rỗng, trả `422`, không publish notification không có recipient.
4. Snapshot và receipt uniqueness giữ nguyên: membership/account thay đổi sau publish không thêm/bớt receipt đã tạo; retry cùng actor/key/full canonical payload trả resource cũ, key khác actor/payload trả `409`.
5. `DEFAULT_SCHOOL` vẫn được validate tại backend dù current app single-school; lookup không tin `schoolScope` do client gửi vì endpoint không nhận scope override.
6. `SCHOOL` giữ nguyên ngoài plan này. Không dùng lookup `INDIVIDUAL` như định nghĩa ngầm cho audience toàn trường.

## 8. FE handoff (không phải FE implementation)

Sau khi BE contract được approved và implemented, hand off cho FE agent:

- Add typed lookup functions for the two approved GET endpoints; send `page` and `size`, consume `ResultPaginationDTO` metadata exactly.
- Audience selector must use lookup `userId`/`classId`; for create send `INDIVIDUAL + recipientUserIds` or `CLASS + targetReference`, never both and never a comma-string ID list.
- Preserve selected values/input on `400/422/409`; show `403` without clearing session; rely on existing `401` convention. Do not cache selector results across account/school scope changes.
- Treat lookup result as provisional: publish can still return `404/422/409` after eligibility re-check. Do not calculate recipient snapshot/count in FE or expose manager-only targeting to recipient view.
- FE contract tests must cover zero-based pagination, q serialization, canonical request shape, empty state and stale-selection error. This handoff authorizes no FE code.

## 9. Acceptance criteria và validation plan sau implementation

Acceptance:

- Only `ADMIN`/`ACADEMIC_OFFICE` can lookup and compose; `TEACHER`/`STUDENT` receive `403` while authenticated recipient flows remain unchanged.
- Lookup search/pagination runs in backend and returns only approved-policy eligible candidates in `DEFAULT_SCHOOL` scope without excess PII.
- `INDIVIDUAL` accepts only deduplicated canonical user IDs; `CLASS` accepts only canonical class ID; forged, missing, inactive, out-of-year or stale candidates are rejected at create/publish according to approved error matrix.
- Publish resolves one snapshot and creates at most one receipt per recipient; a later membership change does not mutate existing receipts.
- Same actor/idempotency key/equivalent canonical payload is idempotent; changed actor/payload returns `409`; notification v2 and existing recipient privacy stay unchanged.
- No migration is added unless the approved contract checkpoint demonstrates a necessary data constraint/index and its Flyway compatibility is reviewed.

Future validation (not run in this planning task): focused notification unit/service/controller tests for search/page/role/scope/existence/eligibility/dedup/snapshot/idempotency; integration tests for `400/401/403/404/409/422`; then project backend validation workflow (test, Checkstyle, PMD, build, JaCoCo and Flyway/runtime evidence) reports each gate separately. Existing repository PMD/full-test baseline failures must remain separately reported, never relabeled as this slice passing.

## 10. Risks and mitigations

- **Authorization/PII leak:** manager-only lookup, minimal projection DTO, no raw entity response, and recipient privacy mapping retained.
- **Stale selector results:** lookup is advisory; create/publish performs authoritative re-check in one transaction boundary.
- **Roster ambiguity:** A02 prevents silently resolving historical/completed enrollment or class lifecycle variants.
- **Idempotency drift:** canonical sort/dedup applies before target snapshot/fingerprint; legacy rows remain null-safe/read-compatible.
- **Performance/N+1:** use paged projection/query and inspect query plan before proposing an index; never `findAll()` then filter in memory.
- **Scope creep:** v2, FE and policy/lifecycle work are explicitly excluded; repository additions outside listed paths require amendment.
