# Developer Plan 015.1: StudentInfo Cardinality, Document và Student Detail API

## 1. Mục tiêu

- Chốt và đồng bộ tài liệu với domain rule: mỗi `Student` trong application có đúng
  một `StudentInfo` (`optional = false`), nhưng `dateOfBirth`, `address` và
  `averageScore` của StudentInfo đều có thể là `null`.
- Đồng bộ rule `studentName` tối đa 35 ký tự ở backend persistence và request
  validation theo quyết định người dùng ngày 2026-08-19.
- Xác nhận API Student hiện có, bổ sung `GET /api/v1/students/{studentId}` đang thiếu
  để frontend mở màn hình Edit an toàn sau refresh/direct URL, và bảo vệ response
  contract bằng integration test.

## 2. Bằng chứng hiện trạng

### 2.1 Quan hệ Student và StudentInfo

- `Student.studentInfo` là inverse side: `@OneToOne(mappedBy = "student",
  cascade = ALL, orphanRemoval = true, fetch = LAZY, optional = false)`.
- `StudentInfo.student` là owning side: `@OneToOne(optional = false)` với
  `@JoinColumn(name = "student_id", nullable = false, unique = true)`.
- Do FK unique, một StudentInfo thuộc đúng một Student và không thể có hai
  StudentInfo cùng tham chiếu một Student. Cascade/orphan removal xử lý lifecycle
  aggregate; integration test hiện có đã xác nhận DELETE Student xoá StudentInfo.
- Các cột `student_info.date_of_birth`, `address`, `average_score` không có
  `nullable = false`; DTO create/update cũng không có `@NotNull`, nên chúng đang là
  optional độc lập với việc StudentInfo bắt buộc tồn tại.

`optional = false` là obligation của association, không có nghĩa từng thuộc tính của
`StudentInfo` phải non-null. FK child-to-parent cũng không tự tạo DB constraint buộc
mỗi row `student` luôn có child row; invariant “mỗi Student có StudentInfo” được duy
trì bởi aggregate service/cascade và sẽ được mô tả chính xác trong tài liệu.

### 2.2 API Student đã kiểm tra

| Endpoint hiện có | Status | Response `data` |
|---|---|---|
| `GET /api/v1/students` | Có | `{ content, page, size, totalElements, totalPages }`; mỗi item là `ResStudentDTO`. |
| `POST /api/v1/students` | Có | `ResStudentDTO`, `201 Created`. |
| `PUT /api/v1/students/{studentId}` | Có | `ResStudentDTO`, `200 OK`. |
| `DELETE /api/v1/students/{studentId}` | Có | Không body, `204 No Content`. |
| `POST /api/v1/students/code` | Có | `{ studentCode }`, `200 OK`. |
| `GET /api/v1/students/{studentId}` | **Chưa có** | Cần thêm trong plan này. |

`ResStudentDTO` hiện gồm chính xác: `studentId: Long`, `studentCode: String`,
`studentName: String`, `dateOfBirth: LocalDate | null`, `address: String | null`,
`averageScore: Double | null`. Success response đi qua envelope chuẩn
`{ statusCode, message, data }`; tất cả Student API yêu cầu authentication theo
`SecurityConfiguration.anyRequest().authenticated()`.

## 3. Phạm vi

### In-scope

- Sửa `Student.studentName` DB mapping từ length 20 lên 35; giữ `studentCode` 10,
  FK/unique constraint và Lombok entity pattern hiện có.
- Sửa `ReqUpdateStudentDTO` từ `@Size(max = 20)` lên 35. `ReqCreateStudentDTO` đã
  là 35 nên không đổi validation logic ngoài kiểm tra nhất quán.
- Giữ `optional = false` ở cả hai đầu association, giữ `StudentInfo` fields nullable
  và viết/điều chỉnh test để chứng minh create/detail response chấp nhận null field.
- Bổ sung GET detail theo id ở controller/service, tái dùng `findStudent` và
  `toStudentDTO`, không expose entity và không tạo DTO response mới.
- Thêm integration test cho detail success, `404` missing, auth boundary phù hợp với
  test setup hiện có, response envelope/field contract, nullable StudentInfo fields,
  name dài 35 và delete aggregate.
- Cập nhật `ApplicationContext.md`, `StudentModule.md`, `DataStructure.md`, Plan 015
  FE và các Developer Plan summary để phản ánh rule/API đã được triển khai thực tế.

### Out-of-scope

- Không đổi API list/search/sort/page, create/update/delete/code generation behavior,
  JWT/security policy, batch CSV, Postman collection hoặc FE production code.
- Không thêm migration framework; project hiện dùng Hibernate `ddl-auto=update`.
  Không tự suy diễn range score, mandatory validation cho birthday/address/score, hay
  schema rule mới ngoài `studentName` length.
- Không thay `Double averageScore` sang `BigDecimal` trong plan này; đó là refactor
  có phạm vi độc lập.

## 4. Thiết kế triển khai

### 4.1 Domain, schema và validation

```text
Student (student_id, student_name NOT NULL VARCHAR(35), student_code UNIQUE)
  1 <--> 1 StudentInfo (info_id, student_id NOT NULL UNIQUE FK)
                    date_of_birth NULL
                    address NULL
                    average_score NULL
```

- `StudentInfo` tiếp tục là owning side vì chứa `student_id`; `Student` giữ aggregate
  lifecycle bằng cascade/orphan removal. Không thêm `@Data`, `@AllArgsConstructor`
  hay `@Builder` vào entity.
- Dù association là mandatory trong application, các cột descriptive của StudentInfo
  giữ nullable; UI/API có thể gửi `null` cho từng field này.
- Do `ddl-auto=update`, kiểm tra bằng integration schema H2 và cấu hình local; nếu
  MySQL existing data/schema không alter được length an toàn thì dừng và báo blocker,
  không tự thêm migration ngoài scope.

### 4.2 Detail API contract

```text
GET /api/v1/students/{studentId}
  -> StudentService.getStudent(studentId) (@Transactional(readOnly = true))
  -> findStudent(studentId)
  -> toStudentDTO(student)
  -> 200 { statusCode, message, data: ResStudentDTO }

missing id -> 404 RestResponse error hiện có
```

- Controller thêm `@GetMapping("/{studentId}")` với `@PathVariable("studentId")`
  rõ ràng và `@ApiMessage` tiếng Việt nhất quán.
- Response detail dùng cùng `ResStudentDTO` như create/update/list item; không có
  password, JPA entity, `StudentInfo.id`, association object hay field persistence
  nội bộ bị lộ ra ngoài.
- Endpoint được security filter bảo vệ bằng rule `anyRequest().authenticated()` hiện
  có, không cần sửa `SecurityConfiguration`.

### 4.3 Liên kết Plan 015 FE

- Sau khi endpoint được implement/test, cập nhật Plan 015 để coi `GET detail` là
  contract đã có và bỏ blocker load edit theo id.
- FE sẽ map `dateOfBirth` date-only và null fields theo Plan 015; Plan 015 không tự
  thêm fallback route state hay scan list để lấy record detail.

## 6. Test và validation dự kiến

### Test contract

- Create/update chấp nhận `studentName` đúng 35 ký tự và reject 36 ký tự với `400`;
  persisted name không bị truncate.
- Create/detail trả `dateOfBirth`, `address`, `averageScore` là `null` khi request
  gửi null; StudentInfo vẫn được tạo và liên kết với Student.
- `GET /api/v1/students/{id}` trả `200`, envelope `statusCode/message/data`, và đủ
  sáu response fields đúng value; id không tồn tại trả `404` error envelope.
- GET detail không trả JPA association/cycle hoặc field nội bộ; existing list/create/
  update/delete/code tests tiếp tục pass, đặc biệt delete xoá aggregate.
- Endpoint protected: test security boundary phù hợp pattern integration hiện có,
  không làm public Student detail vô ý.
