# Plan 076.17 — SSE badge connection synchronization

- Application-document version: **v3**.
- Status: **APPROVED — implemented and validated**. User approved the diagnosis, scoped SSE/badge fix, regression tests and live two-session validation with `good`.
- Related baseline: [Plan 076.16](../../be/notification/076.16-notification-inbox-sse-2026-10-01.md).
- Requirement: online recipients see notification unread badge changes after publish without refreshing the page; retain Bearer JWT, the payload-free `inbox-changed` hint and single-instance delivery.

## Findings and scope

Live local HTTP publish delivers `event:inbox-changed` and the Chrome badge updates on the attendance screen. The original failure is intermittent and has not been reproduced in that steady-state flow. A deterministic gap exists at startup: the shell starts the unread REST request alongside stream establishment, while the stream client refreshes only on subsequent connections. A publish between the initial REST snapshot and SSE subscription is missed.

Synchronize unread count/inbox on every successful stream connection, including the first one. Preserve event callbacks and reconnect backoff. No visual changes, backend changes, dependencies, polling, schema changes or deployments. Preserve existing uncommitted work.

## Implementation and files

- `FE/src/services/notificationApi.ts`: invoke the existing synchronization callback after establishing each successful stream, closing the initial subscription gap.
- `FE/src/services/notificationApi.spec.ts`: regression cases for initial connection without any event, delayed first connection after an old REST snapshot, fragmented live frames, reconnect resynchronization, auth failures and stop cleanup.
- `FE/src/views/shell/AuthenticatedV2ShellView.spec.ts`: exercise the actual stream client with a deferred HTTP response and real layout; assert badge changes after connection without navigation/reload.
- Dev Note and FE/global summaries: record live evidence, gates and limitations.

## Risk and expected output

One extra REST synchronization on initial connection is intentional. Existing latest-request protection prevents an older mount response from overwriting the refreshed badge. Live steady-state success does not prove the user's intermittent failure was caused by the startup gap; report that distinction explicitly. Backend gates are NOT RUN because backend source is unchanged.
